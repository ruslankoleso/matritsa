# Тестовые сценарии

Документ состоит из двух частей: сценарии для ручной проверки (что нажать и что должно произойти) и перечень автоматических тестов. Все данные синтетические, пароль у всех пользователей `demo1234`.

## Подготовка

```bash
docker compose up --build
```

Сайт: http://localhost:3000. Если сборка падает из-за кириллицы в пути к папке, см. раздел «Запуск» в [README](../README.md).

При первом запуске система сама создаёт набор заявок для демо-людей (`client1`–`client11`), поэтому большинство исходов видно без ввода данных: автоматические предложения и отказы, рассмотрение сотрудником, запрос уточнения, встречное предложение, выдача, отказ от предложения, отозванная заявка, черновик.

## Автоматические тесты

### Серверная часть (Go)

Запуск: `docker compose up -d postgres && go test ./... -race`. Интеграционным тестам нужен PostgreSQL на `localhost:5433`, адрес можно изменить переменной `TEST_DATABASE_URL`.

| Пакет | Что проверяют |
|---|---|
| `workflow` | Допустимые и недопустимые переходы, достижимость всех состояний, терминальные состояния, сообщения клиенту для каждого статуса, актуальность диаграммы состояний |
| `scoring` | Ступени каждого из 12 критериев, правило «нет данных — 0 баллов», соответствие 590-П, баллы и границы классов, жёсткие стопы, нулевая выручка, аннуитетный платёж, предельная сумма, DSCR с платежом по новому кредиту (большая заявка не получает баллов больше), формула ожидаемых потерь (EAD — средний долг по графику), монотонность по классу, сроку и сумме, надбавка к ставке |
| `decision` | Совет клиенту после отказа по причине (при жёстком стопе — без «подайте на меньшую сумму»), Встречная сумма оценивается отдельно (класс D на большой заявке не мешает встречному предложению), автоматическое предложение, передача сотруднику, встречная сумма, отказ по классу D, жёсткому стопу, балл бюро как условие автоматического решения, пробел в данных означает ручную проверку и в одну, и в другую сторону и недостаточной доступности, ставка с надбавкой за риск |
| `products` | Каталог, лимиты, валидация, доля потерь по продуктам |
| `pipeline` | Сквозные сценарии по состояниям, недостающие документы, сбой источника и повторы, ручная проверка, конфликт версий, одновременные действия клиента и сотрудника, события и уведомления, истечение предложения |
| `httpapi` | Авторизация, роли, ограничение попыток входа, валидация, идемпотентность, загрузка и выдача документов (владельцу и аналитику, чужому — 404), решения сотрудника, SSE по билету (токен доступа в адресе не принимается), совет после отказа по причине, история клиента без служебных заметок, показатели процесса, соответствие ответов описанию OpenAPI, проверки состояния |
| `seed` | Демо-компании дают задуманные исходы, уникальность логинов и ИНН, большая заявка не получает баллов больше, встречная сумма оценивается отдельно |
| `integrations`, `mocks` | Клиенты бюро и реестра, поведение смоделированных источников и имитация сбоя |
| `ai` | Запасной режим на правилах, проверка ответа модели и пересказа оценки (цифры только из фактов), отказ от неизвестного продукта, эталонный набор из 17 вопросов (`GoldenSet`): поведение справочника и защита от выдумывающей модели |
| `auth`, `config`, `events`, `feed`, `store` | Токены, билет потока событий и пароли, конфигурация, рассылка событий и доставка между экземплярами API через LISTEN/NOTIFY, лента и даты по Москве, слой хранения и блокировка заявки для конвейера |
| `backtest` | Карта ранжирует синтетический риск (Gini выше порога и ниже потолка), доля дефолтов растёт от A к D, AUC на известных случаях |

### Веб-приложение

Запуск: `cd web && npm ci && npm test`.

Проверяются форматы денег, процентов и дат (московское время), график платежей и переплата, список документов, совет после отказа, главная без повторов заявки, вкладки показателей, маршрут статусов, валидация мастера заявки, форма входа, защита маршрутов по ролям, помощник, компоненты ввода (поле суммы, ползунок, загрузка документов), анимация чисел, переключение темы, лендинг.

### Сквозные сценарии (Playwright)

`make e2e` поднимает отдельный стек (проект `matritsa-e2e`, сайт на :3100, свои база и тома), прогоняет тесты и удаляет его: демо-аккаунты основного стека остаются чистыми. Файл [flows.spec.ts](../e2e/flows.spec.ts):

1. Надёжная компания получает предложение, принимает его, видит выдачу денег.
2. Пограничный случай уходит сотруднику, он делает встречное предложение, клиент видит его без перезагрузки.
3. Ликвидированная компания получает отказ с причинами.
4. Сотрудник запрашивает уточнение, клиент отвечает, заявка возвращается сотруднику.
5. Роли разделены, неверный пароль объяснён.
6. После выхода и входа под другим аккаунтом не остаётся данных прежнего; логотип ведёт на главную кабинета.
7. Профиль открывается из меню и показывает ФИО, логин, компанию и статус согласия.
8. Новый человек регистрируется по ИНН компании, попадает в кабинет и входит снова; повторная регистрация той же компании отклоняется.

### Быстрая проверка

`make smoke` или `BASE_URL=http://localhost:3000 go run ./cmd/smoke` проходит три сценария через HTTP-интерфейс без браузера.

## Известные пробелы

- Нагрузочные тесты не проводились.
- Параметры оценки риска проверяются на согласованность, монотонность и различающую способность на синтетическом портфеле (`go run ./cmd/backtest`), но не на реальной статистике дефолтов: её нет ([scoring.md](scoring.md#проверка-на-синтетическом-портфеле)).
- Доступность интерфейса проверялась вручную и инспектором страницы, автоматического аудита в сквозных тестах нет.
