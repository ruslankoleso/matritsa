# Умный кредитный кабинет предпринимателя — дизайн-документ

Дата: 2026-10-21 · Дедлайн хакатона: 2026-10-26 · Команда: **МАТРИЦА РУСИ** · Имя продукта: **«Матрица»** (мой выбор в связке с названием команды; настраивается одной правкой)

Источник требований: «Альфа Хак. Умный кредитный кабинет предпринимателя» (PDF кейса, 16 стр.), обсуждение с командой.

## 1. Зачем это делаем

Предприниматель без банковской экспертизы не понимает, какой кредит ему нужен, что от него требуется и что происходит с заявкой после отправки. Банку нужно обрабатывать много разных заявок и управлять процессом в одном продукте.

Строим **работающий прототип цифрового кредитного конвейера**: клиентский кабинет, рабочее место сотрудника банка и единая бизнес-логика между ними. Цель — выиграть хакатон: показать целостный сквозной процесс, который можно запустить одной командой и пройти руками.

Критерии жюри (стр. 9 кейса), по которым оптимизируем:
1. Целостность — связный путь от потребности до результата.
2. Качество UX для клиента и банковской стороны.
3. Согласованность модулей — данные сохраняются, статус меняется последовательно.
4. Enterprise-подход — безопасность, надёжность, масштабирование, сопровождение.
5. Потенциал развития — объяснённые решения и ограничения.
6. Готовность к проверке — запуск, инструкции, тестовые данные.

## 2. Цели, не-цели, анти-цели

**Цели**
- Сквозной сценарий: подбор продукта → заявка → документы → проверки → скоринг → решение → принятие условий → смоделированные подписание и выдача.
- Две роли: предприниматель и сотрудник банка. Обе работают с одной заявкой в реальном времени.
- Нелинейный результат: одобрение, одобрение на других условиях (встречное предложение), запрос уточнения, отказ.
- Прозрачный скоринг с объяснением факторов.
- Персональная лента предложений в кабинете, меняющаяся под клиента (стр. 7 кейса).
- Красивый, тёплый, «человечный» интерфейс в узнаваемом стиле Альфа-Банка.
- Полный комплект артефактов для жюри (раздел 9).

**Не-цели**
- Не воспроизводим весь банковский кредитный процесс (кейс прямо это не требует, стр. 8).
- Нет реальных интеграций, подписей, выдачи денег, платёжных систем.
- Нет мобильного приложения (запрещено), нет email/SMS/мессенджеров в сценарии.
- Нет сложной ML-модели скоринга. Скоринг — прозрачная балльная модель плюс правила.
- Нет роли администратора правил (описываем как развитие).

**Анти-цели (провал, даже если технически работает)**
- Красивый кабинет, который не связан с обработкой: данные не доходят до сотрудника или статус не меняется.
- Шаблонный «нейронный» вид интерфейса.
- Зависимость от платных API или закрытых данных; LLM с закрытыми весами.
- Запуск, требующий ручной настройки больше одной команды.
- Прототип, выдающий себя за настоящий продукт банка (логотип, торговые знаки).

## 3. Ограничения (из кейса, обязательные)

- Только веб-интерфейс. Основной сценарий внутри продукта: без email, SMS, звонков и мессенджеров.
- Автономность: никаких обращений к системам Альфа-Банка; внешние проверки — локальные моки.
- Только синтетические данные, которые команда формирует сама.
- Никаких платных подписок, API, данных. LLM только с открытыми весами.
- Cloud-native, запуск в Docker, единый воспроизводимый способ запуска на обычном ПК. Публикация в облаке желательна.
- Репозиторий GitHub с историей коммитов; зафиксированная версия (commit hash или тег) на момент дедлайна; коммиты после дедлайна не учитываются; доступ для аккаунта жюри `alfa-hack-2026` (для приватного репозитория).
- Lock-файлы / зафиксированные версии языка и библиотек.
- В репозитории: README.md, THIRD_PARTY_NOTICES, архитектурная схема, описание API, OpenAPI/Swagger, коллекция запросов, диаграмма состояний заявки, модель данных, тестовые сценарии, синтетические данные, тестовые учётные записи.
- Демонстрация — на работающем прототипе, не на заготовленных экранах.

## 4. Решения (принятые вместе с командой)

- Стек бэкенда: **Go**.
- Структура продукта: **лендинг → вход → кабинет по роли**. Предприниматель попадает в клиентский кабинет, сотрудник — на рабочее место обработки заявок.
- Визуальный стиль: **в духе Альфа-Банка** (красный акцент, белое, крупная жирная типографика), но **тёплый и знакомый, как помощник**. Без официального логотипа и торговых знаков.
- Лента «новостей» из стр. 7 кейса понимается как **персональная лента предложений** и подсказок, меняющаяся под клиента.
- Код пишет Claude; команда проверяет и принимает результат.
- Навыки по фронтенду: `taste-skill`, `framer-motion` (установлены), `frontend-design`, `ui-ux-pro-max`, `ui-styling`.

## 5. Мои решения (builder's calls) — команда может изменить

| Решение | Выбор | Почему |
|---|---|---|
| Имя продукта | «Матрица» (подпись «команда МАТРИЦА РУСИ») | Связано с названием команды; не бренд банка |
| Фронтенд | React + TypeScript + Vite, Tailwind, shadcn/ui, Framer Motion | Скорость, качество, доступные компоненты |
| HTTP-роутер | chi | Лёгкий, стандартный стиль Go |

| БД | PostgreSQL, pgx, sqlc, миграции goose | Надёжность, типобезопасность |
| Реальное время | Server-Sent Events (SSE) для статуса заявки и ленты | Проще WebSocket, достаточно для односторонних обновлений |
| Авторизация | Логин + пароль (bcrypt), JWT access + refresh, RBAC по ролям | Без SMS и писем, как требует кейс |
| Хранение файлов | Локальный том (Docker volume) | Автономно |
| ИИ | Ollama + малая открытая модель (Qwen-класса); запасной вариант на правилах/шаблонах | Требование открытых весов; прототип работает и без модели |

| Шрифт | Бесплатный (Onest или Golos), не фирменный шрифт банка | Требование бесплатных ресурсов |

## 6. Модель кредитного процесса

### 6.1. Границы
Начало — потребность клиента в финансировании. Конец — решение и (смоделированная) выдача. Вне границ: погашение, сопровождение кредита, коллекшн.

### 6.2. Роли и действия
- **Предприниматель:** выбирает цель и продукт, заполняет заявку, загружает документы, отвечает на запросы уточнений, принимает или отклоняет предложение, подписывает (имитация).
- **Сотрудник банка (кредитный аналитик):** берёт заявки из очереди, видит данные, проверки и разбор скоринга, принимает решение вручную в серой зоне, запрашивает уточнения, меняет условия.
- **Система:** проверка полноты, обогащение данными (моки БКИ и ЕГРЮЛ), скоринг, автоматическое решение на крайних значениях, журнал событий.

### 6.3. Продукты (синтетические)
1. Оборотный кредит — пополнение оборотных средств.
2. Кредит на оборудование — инвестиционный, с залогом приобретаемого.
3. Овердрафт — лимит на расчётном счёте.
4. Экспресс-кредит — малая сумма, ускоренное решение.
У каждого свои границы суммы и срока, базовая ставка, перечень документов, допустимые уровни риска.

### 6.4. Состояния заявки (диаграмма будет в docs/)

`DRAFT` → `SUBMITTED` → `INTAKE_CHECK` → (`NEEDS_INFO` ⇄ клиент дополняет) → `ENRICHMENT` → `SCORING` → `DECISION`:
- автоодобрение (высокий балл, малая сумма) → `OFFER_MADE`
- серая зона → `ANALYST_REVIEW` → `OFFER_MADE` | `NEEDS_INFO` | `REJECTED`
- жёсткий стоп (ликвидация, критичная просрочка) или низкий балл → `REJECTED` (с причинами)

`OFFER_MADE` → клиент принимает → `SIGNING` (имитация) → `DISBURSED` (имитация); клиент отклоняет → `DECLINED_BY_CLIENT`; истёк срок предложения → `EXPIRED`; клиент отзывает заявку → `CANCELLED`.

Каждый переход: проверка допустимости, запись в журнал (кто, когда, причина), событие для SSE.

### 6.5. Скоринг и решение
Различаем **скоринг** (оценка риска) и **кредитное решение** (условия), как требует кейс (стр. 14).
- **Скоринг:** балльная модель 0–100, факторы с весами: возраст бизнеса, выручка и её стабильность, долговая нагрузка (платежи / выручка), кредитная история из БКИ (просрочки, действующие обязательства), статус по ЕГРЮЛ, соотношение суммы к выручке, группа риска по ОКВЭД. Результат — балл, класс риска A–E и **список вкладов факторов** (почему так).
- **Решение (правила по продуктам):** hard-stop правила; затем по классу риска и продукту — одобрить на запрошенных условиях, предложить **встречные** (меньше сумма, другой срок, другая ставка, другой продукт), запросить уточнение или отказать. Ставка = базовая ставка продукта + надбавка за риск.
- Все пороги и веса вынесены в конфигурацию и описаны в документации.

### 6.6. Внешние интеграции (моки)
- **mock-bki:** по ИНН возвращает действующие обязательства, долг, максимальную просрочку, кредитный балл.
- **mock-egrul:** по ИНН возвращает статус, дату регистрации, ОКВЭД, директора, признаки риска.
Детерминированные ответы по ИНН. Клиент интеграции в основном сервисе работает по HTTP с таймаутами и ретраями; при недоступности моков заявка получает понятный статус ожидания, а не падает.

## 7. Что видит пользователь

### 7.1. Лендинг (публичный)
Что это, как работает путь «заявка = маршрут», кнопка «Войти». Идея: **маршрут** (линия с остановками) как визуальный мотив. Живая деталь: калькулятор — ползунки суммы и срока, платёж пересчитывается на глазах.

### 7.2. Вход
Один экран входа для всех ролей, маршрутизация по роли. Тестовые аккаунты и кнопки быстрого входа «как предприниматель» / «как сотрудник банка» (для жюри).

### 7.3. Кабинет предпринимателя
- Главная: персональная лента предложений и подсказок, активные заявки.
- Подбор продукта: диалоговый помощник (ИИ либо правила) → рекомендация продукта и условий.
- Мастер заявки: пошагово, сохранение черновика на каждом шаге, объяснение, зачем нужны данные; автозаполнение данными компании по ИНН через мок.
- Документы: чек-лист по продукту, загрузка файлов.
- Статус: маршрут заявки с текущей остановкой и «что дальше»; уведомления внутри продукта.
- Предложение: условия (возможно, встречные), принять / отклонить; имитация подписания.

### 7.4. Рабочее место сотрудника
- Очередь заявок с фильтрами и приоритетами.
- Карточка: данные клиента и компании, результаты мок-проверок, разбор скоринга (вклад каждого фактора), история событий.
- Действия: одобрить, изменить условия, запросить уточнение, отказать, с обязательным комментарием; пояснение решения человеческим языком (ИИ либо шаблон).

### 7.5. Персональная лента
Карточки генерируются правилами из профиля: ОКВЭД, размер и возраст бизнеса, выручка, обязательства, этап заявки. Примеры: подходящий продукт для отрасли, недостающие документы, возможность сопутствующего продукта после выдачи. На демо переключаем клиента — лента перестраивается.

### 7.6. Визуальный язык
Красный только на главном действии; белая основа с мягкими тоновыми ступенями; крупная типографика; без градиентов, стекла, свечений, иконок-в-плитках, рядов одинаковых карточек и выдуманных цифр. Нарисованные иллюстрации в стиле продукта; тёплые тексты на «вы» («Расскажите, на что нужны деньги», а не «Укажите цель кредита»). Анимации умеренные, с учётом prefers-reduced-motion. Режимы по taste-skill: лендинг — «page», кабинеты — «app screens». Лендинг — направление «один мотив», кабинеты — «тихий инструмент».

## 8. Где применяем ИИ (только где есть ценность)
1. Помощник подбора продукта: свободный текст («нужно закупить станок») → цель, продукт, ориентировочные параметры. Запасной вариант: правила по ключевым словам.
2. Пояснение решения аналитику и клиенту человеческим языком по факторам скоринга. Запасной вариант: шаблоны.
3. Задел (если останется время): распознавание полей из загруженных документов.
ИИ никогда не принимает решение — только объясняет и подсказывает.

## 9. Enterprise и артефакты для жюри

**Качество системы:** слоистая архитектура (handler → service → repository), конфигурация через переменные окружения, миграции, структурное логирование, health/readiness-эндпоинты, graceful shutdown, ограничение частоты запросов, валидация входа, RBAC, аудит-журнал переходов, идемпотентность отправки заявки, транзакции при смене статуса, таймауты и ретраи к внешним сервисам.

**Артефакты в репозитории:** README (назначение, архитектура, окружение, запуск, переменные, компоненты, пошаговый сценарий проверки), архитектурная схема, `api/openapi.yaml`, коллекция запросов, диаграмма состояний, модель данных (ER), тестовые сценарии, синтетические данные (5–6 компаний: надёжная, закредитованная, молодая без истории, ликвидированная, пограничная и др.), тестовые учётки, THIRD_PARTY_NOTICES (с пометкой смоделированных интеграций), lock-файлы (`go.sum`, `package-lock.json`), Dockerfile'ы и `docker-compose.yml`.

**Тесты:** юнит-тесты машины состояний и скоринга (table-driven), интеграционные тесты API с реальной БД в контейнере, E2E на Playwright (главный сценарий и сценарий встречного предложения).

## 11. Риски

- **ИИ-модель тяжёлая для обычного ПК.** Смягчение: малая модель, запасной режим без неё, отключение флагом.
- **Объём.** Смягчение: порядок работ по ценности, сначала сквозной сценарий, потом красота и ИИ.
- **Два UI (клиент и сотрудник).** Смягчение: общие токены и компоненты.
- **Docker на чистой машине.** Смягчение: проверка запуска с нуля до заморозки.

## 12. Что остаётся строителю

Конкретные пороги и веса скоринга, тексты помощника и ленты, точный набор полей анкеты, названия и описания продуктов, иллюстрации, структура пакетов Go, внутренние контракты событий.
