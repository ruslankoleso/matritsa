# Матрица — умный кредитный кабинет предпринимателя

**Сайт:** https://matritsa-rusi.ru · **Код:** https://github.com/ruslankoleso/matritsa · **Презентация:** [PDF](presentation/Матрица_презентация.pdf) · **Видео:** приложено к заявке · **Запуск:** `docker compose up --build` → http://localhost:3000

Прототип цифрового кредитного конвейера для малого и микробизнеса. Команда **МАТРИЦА РУСИ**, хакатон «Альфа Хак» (кейс «Умный кредитный кабинет предпринимателя»).

Продукт соединяет клиентский путь и внутреннюю обработку заявки в один процесс: предприниматель выбирает продукт и подаёт заявку в кабинете, система проверяет данные и считает прозрачную оценку, а сотрудник банка принимает решение там, где нужен человек. Клиент видит каждый шаг и понимает, что делать дальше.

> Прототип. Внешние системы (БКИ, ЕГРЮЛ/ФНС), подписание документов и выдача денег **смоделированы**, все данные **синтетические**. Стиль вдохновлён брендом из кейса; официальный логотип, шрифт и торговые знаки не используются.

## Запуск (одна команда)

Нужен только **Docker** (Compose v2). Ни Go, ни Node устанавливать не требуется.

```bash
docker compose up --build
```

Через 1–2 минуты (первая сборка дольше) откройте:

| Что | Адрес |
|---|---|
| Сайт: лендинг, вход, кабинеты | http://localhost:3000 |
| Описание API (Swagger UI) | http://localhost:3000/docs/ |
| API напрямую (только с этого компьютера) | http://localhost:8080/api/v1 |

Остановить: `docker compose down` (данные сохраняются), полный сброс: `docker compose down -v`.

Наружу открыт только сайт (:3000). API, моки и база слушают лишь `127.0.0.1`: извне к API ходят через nginx, который сообщает адрес клиента для ограничения попыток входа.

> Если сборка падает с ошибкой `x-docker-expose-session-sharedkey ... non-printable ASCII`, в пути к папке проекта есть кириллица. Скопируйте проект в папку с латинским путём или запустите сборку через символическую ссылку с латинским именем.

### Часть 1. Клиент: регистрация и заявка (окно 1)

1. На сайте нажмите **«Войти»**, затем вкладку **«Регистрация»**.
2. Заполните: **ФИО** — любое, например `Иванов Иван Иванович`; **Логин** — латиницей, от 3 символов, например `jury1`; **Пароль** — не короче 8 символов, например `Jury-2026`. Нажмите **«Дальше»**.
3. **ИНН компании:** `7700000023` — ООО «Векторснаб», закредитованная компания: аналитик предложит меньшую сумму. Компания подтянется из реестра (смоделированного). Справа от формы есть список других тестовых ИНН с описанием исхода; если ИНН уже занят другим проверяющим (одна компания — один аккаунт), выберите там другой, например `7700000009` (пограничный случай). Отметьте согласие и нажмите **«Создать аккаунт»**.
4. В стартовом окне введите потребность: `Пополнить оборотные средства перед сезоном, около 3 млн на 2 года` и нажмите **«Создать заявку»**.
5. В мастере нажмите **«Подобрать»** — помощник предложит «Кредит на оборотные средства», нажмите **«Выбрать продукт»**. Проверьте поля: **сумма** `3 000 000`, **срок** `24` месяца. Нажмите **«Далее»**.
6. Шаг «Компания» заполнен из реестра — нажмите **«Далее»**.
7. Шаг «Документы»: загрузите **выписку** и **отчётность** из таблицы выше. Нажмите **«Далее»**, затем **«Отправить заявку»**.
8. Маршрут заявки пройдёт этапы сам: проверка полноты → сверка с реестром и бюро → оценка — и остановится на **«У сотрудника банка»**. Пока ждёте, откройте чат справа внизу и спросите, например, `Что с моей заявкой?` или `Какие документы нужны для овердрафта?`. Откройте главную кабинета: блок **«Для вашего бизнеса»** — лента предложений, её карточки зависят от компании и меняются после заявки. Нажмите колокольчик справа вверху: на каждом шаге в уведомлениях появляется новая запись по вашей заявке, полная страница открывается по ссылке «Открыть все уведомления». **Окно не закрывайте.**

### Часть 2. Аналитик банка: решение (окно 2, инкогнито)

9. Откройте сайт, нажмите **«Войти»** и кнопку быстрого входа **«Анна Белова»** (или логин `staff1`, пароль `demo1234`).
10. В очереди откройте заявку **«Векторснаб»** (или компании, которую вы зарегистрировали).
11. Посмотрите вкладки: **«Оценка»** (класс A–D, нагрузка на выручку и DSCR, ожидаемые потери PD × LGD × EAD, заключение, категория 590-П), **«Все критерии»** (12 критериев с пояснениями), **«Источники и документы»** (реестр, бюро, ваши файлы открываются), **«Журнал»**.
12. Справа — рекомендация системы. Нажмите **«Другие условия»**: сумма, срок и ставка уже заполнены рекомендацией; добавьте комментарий, например `Предлагаем сумму, платёж по которой посилен`, и отправьте.

## Как мы пришли к решению

Начинали с процесса, а не с экранов:

1. **Кейс и практика банков.** Два режима: быстрое решение по правилам для простых заявок и рассмотрение аналитиком для остальных; DSCR рядом с долговой нагрузкой; профессиональное суждение банка.
2. **Разговор с предпринимателем.** Обсудили путь клиента с владельцем малого бизнеса — компании Karma Group.
3. **Таблица кредитного аналитика.** 12 критериев на 100 баллов, классы A–D, соответствие категориям 590-П, стоп-факторы ([docs/analyst/](docs/analyst/)).
4. **14 вопросов аналитику** с примерами в рублях — там, где таблице не хватало границ или формул. 19 её решений вошли в модель ([docs/scoring.md](docs/scoring.md#решения-аналитика-по-вопросам-модели)).
5. **Сравнение открытых языковых моделей** на 17 вопросах клиентов ([docs/ai-chat.md](docs/ai-chat.md)).

### Кредитный процесс

Заявка проходит состояния `DRAFT → SUBMITTED → INTAKE_CHECK → ENRICHMENT → SCORING` и затем:

- **автоматически** `OFFER_MADE` (высокая надёжность и небольшая сумма) или `REJECTED` (жёсткий стоп или низкая оценка);
- **к сотруднику** `ANALYST_REVIEW` (серая зона), который одобряет, предлагает другие условия, запрашивает уточнение (`NEEDS_INFO`) или отказывает;
- клиент принимает предложение → `SIGNING → DISBURSED` (имитация), отказывается, или предложение истекает через 7 дней.

Оценка разделена на три вопроса: **кто заёмщик** (баллы, класс, вероятность дефолта PD), **что потеряет банк при дефолте** (EL = PD × LGD × EAD, где EAD — средний долг по графику) и **потянет ли бизнес платёж** (нагрузка на выручку и DSCR). Класс относится к заявке: DSCR в баллах считается с платежом по новому кредиту, поэтому большая сумма даёт меньше баллов; такая заявка уходит на встречные условия, и меньшая сумма оценивается отдельно. Формулы и допущения: [docs/scoring.md](docs/scoring.md). Параметры модели иллюстративные, не откалиброваны на реальных данных. Различающая способность проверена на синтетическом портфеле: `go run ./cmd/backtest` (Gini 0,23 при потолке 0,57, классы упорядочены по доле дефолтов; выводы — в [scoring.md](docs/scoring.md#проверка-на-синтетическом-портфеле)).

## Помощник в кабинете

В правом нижнем углу кабинета клиента есть кнопка чата. Помощник отвечает **только** по кредитам для бизнеса и работе кабинета: продукты, документы, сроки, ставки, оценка, статус ваших заявок. Остальное блокируется в коде до обращения к модели, поэтому уговорить его сменить тему нельзя:

1. вопрос не по теме и попытки изменить правила («игнорируй инструкции», «притворись…») отклоняются сразу;
2. точные вопросы (документы, ставки, сроки, статус, оценка) отвечает справочник из каталога продуктов и собственных заявок человека; если ответа в нём нет, помощник так и говорит и предлагает сотрудника, а не выдумывает;
3. модель, если она включена, подбирает продукт и поясняет предыдущий ответ; её ответ проверяется кодом (цифры, обещания, длина, тема) и при сомнении заменяется ответом справочника;
4. сообщение не длиннее 500 символов, не более 30 сообщений за 10 минут.

Клиент может позвать сотрудника кнопкой «Связаться с сотрудником» или словами. Разговор попадает специалисту поддержки (`support1`), пока тот не подключился, отвечает помощник, после подключения пишет специалист в том же окне. Специалист видит статусы заявок клиента, но не оценку и не решения.

Помощник никогда не принимает решение по заявке. Сравнение ИИ и справочника, причины выбора и устройство подключения сотрудника: [docs/ai-chat.md](docs/ai-chat.md).

## ИИ (по желанию)

> **Для проверки ИИ не нужен.** Весь сценарий кредитного конвейера, включая чат помощника и подбор продукта, работает без модели на правилах и справочнике, и именно так его стоит проверять. ИИ-функции реализованы как необязательное дополнение и **в эту версию не вынесены на проверку**: по умолчанию они выключены, подробной инструкции по запуску и проверке нет, а подключение возможно только к Ollama (адрес и название модели задаются, API-ключ и произвольный OpenAI-совместимый сервис пока не поддерживаются). Это в плане доработки; описание ниже даёт общую картину.

Мы проверили открытые языковые модели в роли помощника: T-lite-it-2.1, Qwen3.5 4B и 9B. Модели, которые запускаются на обычном ПК, в части ответов придумывали сроки и условия (T-lite — в 4 из 12 ответов по теме, Qwen3.5 4B — в 3), а справочник на правилах — ни разу. В кредитном общении названный срок или условие клиент воспринимает как обещание банка, поэтому точность важнее живости ответа. **Для показа мы оставили правила**: точные ответы даёт справочник, а модель можно включить одним флагом — тогда она подбирает продукт и поясняет ответы, и каждый её ответ проверяется кодом. Сравнение: [docs/ai-chat.md](docs/ai-chat.md).

ИИ делает только две вещи и **никогда не принимает решение**: подсказывает продукт по описанию потребности и пересказывает факты оценки простыми словами. Любой сбой модели (недоступна, ошибка, мусор в ответе, неизвестный продукт) тихо переключает на правила.

По умолчанию ИИ выключен (`AI_ENABLED=false`), всё работает на правилах. Включить открытую модель локально:

```bash
AI_ENABLED=true docker compose --profile ai up -d --build
./scripts/pull-model.sh        # один раз скачает T-lite-it-2.1 (нужен интернет, ~5 ГБ)
```

На Mac модель заметно быстрее на хосте: `ollama serve` и `ollama pull hf.co/t-tech/T-lite-it-2.1-GGUF:Q4_K_M` на хосте, затем `OLLAMA_URL=http://host.docker.internal:11434 AI_ENABLED=true docker compose up -d`. Почему T-lite и как проверяется ответ модели: [docs/ai-chat.md](docs/ai-chat.md).

## Ограничения и развитие

Что осознанно упрощено:

- оценка — прозрачная балльная модель с расчётом ожидаемых потерь, но PD, LGD и пороги иллюстративные: статистики дефолтов у прототипа нет;
- денежный поток для DSCR берётся из смоделированной выписки; если выписку проанализировать нельзя — оценка по доле выручки отрасли (35 / 30 / 25 %);
- бюро, реестр, подписание и выдача смоделированы, данные синтетические;
- один тип сотрудника, без лимитов полномочий и кредитного комитета; нет роли администратора правил;
- хранилище документов — локальный том; токен сессии в `localStorage`.

Продукты, которые мы знаем и сознательно не включили: кредитная линия, лизинг, кредиты с залогом недвижимости, поручительство третьих лиц — каждый добавляет свой блок проверок. План развития: калибровка модели на данных банка, эти продукты, лимиты полномочий, реальные сервисы подписания и выдачи. Подробнее — в [docs/architecture.md](docs/architecture.md#ограничения-и-развитие) и [docs/product.md](docs/product.md#за-пределами-версии-и-план-развития).
